# 免费版约束下的分批 Cron 刷新、标准 `fetch` 抓取与分层限流

为控制 Workers Free 的 CPU 和外部子请求用量，并适配 Isolate 内存不持久、标准 `fetch()` 不沿用原版固定 IP 传输的运行环境，Worker 版在三个机制上刻意偏离 `local/`：

1. **分批 Cron 刷新**：通过 Workers 原生 Cron Triggers 驱动，每次订阅刷新按最久未更新顺序最多处理 3 条到期订阅（可配置）并带子请求预算控制，其余到期订阅在下一轮 Cron 自动接续，同时沿用 D1 `JobLeaseLock` 防重入；规则索引定时拉取并持久化到 D1。
2. **标准 `fetch()` 订阅抓取**：使用标准 `fetch()` 配合协议白名单、禁止凭据、内网字面量拦截、重定向与响应体上限校验；保留 `/api/settings/source-import` 契约但明确提示边缘节点无法访问本地局域网。
3. **分层限流**：登录与初始化等低频敏感端点基于 Cloudflare 原生 `CF-Connecting-IP` 写入 D1 做跨节点持久限流；高频的订阅 YAML 拉取端点仅做 Isolate 内存尽力限流以节省 D1 免费写额度。

## 备选方案

- **单次全量 Cron 刷新**：订阅或导入源稍多时在免费版极易撞到 50 次子请求或 10ms CPU 上限。
- **全量 D1 限流 / 全量内存限流**：全量 D1 会让客户端高频拉订阅消耗写额度；全量内存则导致登录防爆破在冷启动或跨边缘节点时失效。

## 影响

- 同步上游时保留 Worker 的分批调度、受限 `fetch()` 和分层限流；原版全量 Cron、固定 IP 连接和全内存限流不适用于本部署形态。
- 批次和出站预算不限制单次解析的 CPU。2026-11-25 的独立线上验证中，一次原生订阅 Cron 成功刷新两条测试订阅，Cloudflare 记录 62 ms CPU，超过免费版 10 ms 目标。
