# 领域文档（Domain Docs）

说明工程技能在探索本代码库时应如何读取与遵循领域文档。

本仓库当前采用**单上下文（single-context）**布局。

## 探索代码前先读取以下文档

- 仓库根目录的 **`GLOSSARY.md`**；
- **`docs/adr/`**：阅读与你即将改动区域相关的架构决策记录（ADR）。

如果上述文件或目录尚不存在，直接继续。当术语或架构决策真正确定时，再用 `/domain-modeling` 按需创建。

## 文件结构

本仓库采用单上下文结构：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-example-decision.md
│       └── 0002-another-decision.md
├── packages/
└── local/
```

（如未来业务规模扩大并拆分出多个独立限界上下文，可在根目录引入 `GLOSSARY-MAP.md` 切换为多上下文布局，并在各子上下文目录下维护独立的 `GLOSSARY.md` 与 `docs/adr/`。）

## 遵循术语表词汇

当你的输出涉及领域概念（如 Issue 标题、重构提案、问题假设、测试用例命名）时，应严格使用 `GLOSSARY.md` 中定义的术语，不要随意换成术语表明确规避的同义词。

如果你需要的概念尚未出现在术语表中，这是一个明确信号：要么你引入了项目并不使用的说法（请重新斟酌），要么确实存在领域词汇缺口（记录下来以供 `/domain-modeling` 补充）。

## 显式标注 ADR 冲突

如果你的方案或输出与既有 ADR 相冲突，请明确指出，而不要静默覆盖：

> _与 ADR-0007（示例决策）冲突，但值得重新讨论，因为……_
